> # A basic multi-agent programming framework for achieving multi-agent transactions

  The goal of this proejct is to design a basic programming framework that provides transaction guarantees to 
  multiple agents that collaborate to accomplish a user task. We target the following agent scenarios: 

  * Database operations include local DBs and remote cloud object stores / cloud DBs that the user/agents have 
  full control over. 
  * File system operations include local file and directory operations and configuration changes. 


  # Problems this design tackles

  LLM-backed agents can generate workflows based on user prompts. A prompt-genrated workflow may touch and modify 
  the state of one of multiple data sources spanning local/remote DBs/cloud storage systems and file systems. 
  Multilpe agents may collaborate to accomplish a task together. Different agents may touch or modify the same 
  data source, same data entries, and same files/directories. 

  Traditionally, these operations that engage with a single goal are typically protected with transaction 
  semantics. For example, different microservies that engage with hotel booking need transactions in order to 
  guarantee atomicity, idempotence, and exactly-once semantics. See [Beldi 
  OSDI'20](https://www.usenix.org/conference/osdi20/presentation/zhang-haoran) and [Olive 
  OSDI'16](https://www.usenix.org/conference/osdi16/technical-sessions/presentation/setty). Agents need 
  transaction semantics as well. Unlike traditional programmed processes, agents are intelligent, 
  non-deterministic, and sometimes make mistakes (hallucinating). Therefore, it becomes challenging to add 
  transaction support: 

  * Agents that are not coordinated cause race conditions. 
  * Agents that become "over-smart" may do more that violate consistency, correctness.
  * Agents may fail, and the underlying systems (OS, hardware) may fail as well, leaving the workflow in a middle 
  state that is difficult to manually roll back (to achieve all-or-nothing). 


  # Design sketch of a transactional programming framework for multi-agents

  There might be multiple solutions to achieve transaction support for multi-agent workflows. One solution is to 
  design a transactional programming framework that explcitly define the order, relationship, precondition, and 
  semantics of workflow operations performed by different agents. 

  This programming framework would expose APIs like function decorator to indicate that this function implements 
  an operation that is involved in a transaction. The programming framework should also define orders of 
  operations and preconditions of different operations. The programming framework should also avoid race 
  condition. The framework can be built on existing transaction algorithms like 2PC and Saga. Saga with 
  compensation might be a good template for the agent scenarios.

  # Design spec for a mini transactional programming framework for single-file-agents based multi-agent workflows

  Below is a self-contained design spec for a “Tx-Mini” layer that drops cleanly into lightweight agent frameworks
   such as single-file-agents (SFA).
  It tries hard to stay simple enough to prototype in a weekend while still giving you real ACID-style safety 
  across SQLite, the local file-system, and any other resource for which you can implement three tiny callbacks.

  ## 2 Core ideas in 60 s

  Principle    What it means here
  One process, many agents    SFA spawns agent coroutines in the same Python interpreter → we coordinate in-proc 
  (no network consensus).
  Single coordinator, append-only op-log    A Transaction object records every planned action to 
  `~/tx_log/uuid.jsonl`; `fsync` before `COMMIT` ⇒ crash-safe.
  Do / Undo / Prepare    Every resource adaptor exposes those three idempotent methods. If all adaptors implement 
  prepare we run 2PC; otherwise we automatically fall back to a mini-Saga (do-then-compensate-on-abort).
  Decorators + context-manager    Agents stay readable: they just wrap risky calls in @tx_op or with Tx(): ….

  ## Public Python API (stable v0.1)

  ```python
  # tx.py  ──────────────────────────────────────────────────────────────
  from typing import Any, Callable, Awaitable, Protocol, Dict, List

  ###############################################################################
  # 2.1  Resource adaptor protocol – implement this for FS, SQLite, etc.
  ###############################################################################
  class Op(Protocol):
      kind: str          # "fs.write", "db.exec", …
      args: Dict[str, Any]

  class ResourceAdaptor(Protocol):
      async def do(self,  op: Op) -> None: ...
      async def undo(self, op: Op) -> None: ...
      async def prepare(self, op: Op) -> bool: ...   # optional – may raise NotImplementedError

  ###############################################################################
  # 2.2  Transaction context – used directly or via decorator
  ###############################################################################
  class Transaction:
      def __init__(self, name: str = "") -> None: ...
      def register(self, op: Op, adaptor: ResourceAdaptor) -> None: ...

      async def __aenter__(self): ...
      async def __aexit__(self, exc_type, exc, tb): ...

      async def commit(self) -> None: ...
      async def abort(self)  -> None: ...

  ###############################################################################
  # 2.3  High-level helpers
  ###############################################################################
  def current_tx() -> Transaction | None: ...
  def in_transaction() -> bool: ...

  def tx_op(adaptor: ResourceAdaptor):
      """
      Decorator that:
      1) Captures the function call as an Op.
      2) Executes it via adaptor.do() **inside the current Tx**.
      3) If no Tx is active, runs the call immediately (best-effort mode).
      Usage:
          @tx_op(fs_adaptor)
          async def write_file(path: str, data: bytes): ...
      """
      ...

  ###############################################################################
  # 2.4  Convenience adaptors shipped out-of-the-box
  ###############################################################################
  class FileSystemAdaptor(ResourceAdaptor):        # fs.write, fs.rename, fs.delete
      ...
  class SQLiteAdaptor(ResourceAdaptor):            # db.exec, db.query
      ...
  ```


  ## 3 Design choices

  * Op is a plain dict → serialisable to JSON with no custom encoder.

  * tx_op works for both async def and sync functions—handy for existing utilities.

  * Coordinator lives inside `Transaction.__aexit__`; if any prepare() is missing we skip 2PC and run Saga.

  ## Programming model from an agent’s perspective

  ```python
  # blog_builder_agents.py  (single-file style)
  from tx import Transaction, tx_op, FileSystemAdaptor, SQLiteAdaptor
  fs  = FileSystemAdaptor(root="posts/")
  db  = SQLiteAdaptor(database="site.db")

  @tx_op(fs)
  def write_post(slug: str, html: str):
      fs_path = f"{slug}.html"
      return dict(kind="fs.write", args={"path": fs_path, "data": html})

  @tx_op(db)
  def insert_index(title: str, slug: str):
      return dict(kind="db.exec",
                  args={"sql": "INSERT INTO posts(title,path) VALUES(?,?)",
                        "params": (title, f"{slug}.html")})

  async def build_and_index(title, slug, html):
      async with Transaction(name=f"publish:{slug}") as tx:
          await write_post(slug, html)      # recorded, *not* yet durable
          await insert_index(title, slug)   # recorded too
          # nothing else to do; exiting the 'with' runs coordinator
  ```


  If any step raises or the coordinator dies mid-commit, Transaction will:

  1. Replay the op-log on restart.

  2. Either finish a 2PC commit (prepare marks ops “in-progress”) or undo in Saga order.

  ## 4 Resource adaptor sketches

  ### 4.1 FileSystemAdaptor (copy-on-write for free rollback)

  ```text
  * do:     write to temp file; keep {temp -> final} mapping
  undo:   delete temp; ignore if missing
  prepare: rename temp → final (atomic on POSIX) and fsync directory
  ```

  ### 4.2 SQLiteAdaptor (built-in Tx → trivial)

  ```text
  do:     execute SQL on a *savepoint*
  undo:   rollback to savepoint
  prepare: release savepoint (becomes visible); returns True
  ```

  (If you need cross-DB 2PC later, swap prepare to PREPARE TRANSACTION.)

  ## 6 Extending to real clouds later 

  Resource    Minimal change
  S3 / GCS    Implement do = multipart-upload, undo = delete, prepare = HEAD to verify ETag
  Postgres    Switch adaptor to PREPARE TRANSACTION + 2PC commit
  Git    Use work-tree snapshot; prepare = git add && git diff --quiet

  Because the coordinator logic never changes, you just ship new adaptors.
